# VerKer
[![CI](https://github.com/evdenis/verker/actions/workflows/ci.yml/badge.svg)](https://github.com/evdenis/verker/actions/workflows/ci.yml)

ACSL cпецификации к библиотечным функциям ядра Linux

Проект по разработке спецификаций и формальному доказательству корректности библиотечных функций ядра Linux.

# Статус доказательств

Актуальная информация по статусу доказательств отражена в основном [README.md](README.md) файле.

# Инструментарий

Спецификации разрабатываются на языке ACSL. В качестве инструмента формальной верификации
используется штатный [Frama-C](https://frama-c.com/) с плагином
[WP](https://frama-c.com/fc-plugins/wp.html). Патченный Frama-C больше не требуется.

Разработка ведётся на Frama-C 33.0 (Arsenic) с Why3 1.8.2 и солверами Alt-Ergo, CVC4,
CVC5, Z3. Установка через [opam](https://opam.ocaml.org/):

```
$ opam install frama-c why3 alt-ergo z3
$ frama-c -wp-list-provers   # cvc5 в opam нет: ставится отдельно и кладётся в PATH
```

Ранее проект использовал плагин
[AstraVer (Jessie)](https://forge.ispras.ru/projects/astraver). Этот инструментарий больше
не поддерживается, и его поддержка удалена; последнее состояние с AstraVer доступно в
истории git.

# Запуск инструментов

Список доступных целей можно посмотреть командой ```make help```.

## Доказательство

```
$ make wp-strlen          # одна функция
$ make wp                 # все функции
$ make wp-status          # только недоказанные цели
$ make wp-gui-strlen      # то же самое в GUI Frama-C
```

Переменные окружения ```TIMEOUT``` (секунд на цель) и ```PROCESSES``` (параллельных
солверов) настраивают запуск: ```make TIMEOUT=30 wp-strcmp```. Увеличение ```TIMEOUT``` не
влияет на цель, timeout которой уже закеширован, — нужен ```make wp-rebuild```.

Часть целей недоступна SMT-солверам, но берётся тактиками WP (диапазоны полубайтов,
равенства со сдвигом). ```make wp-auto-<функция>``` ищет такое доказательство и сохраняет
скрипт в ```sessions/script/```; обычные запуски его переигрывают. Сейчас такой скрипт не
нужен ни одной функции, поэтому ```sessions/script/``` пуст.

Каждый запуск включает ```-wp-rte```, поэтому проверки времени исполнения входят в
доказательство. Две опции RTE намеренно выключены, потому что обе запрещают преобразования,
которые в C определены и на которые ядро опирается:

- ```-warn-unsigned-overflow``` — идиома ```while (count--)``` в memset, memcpy, memmove
  и подобных на последней итерации проходит через ноль, и завёрнутое значение не
  используется;
- ```-warn-unsigned-downcast``` — побайтовое сравнение ```c = (unsigned char) *s++``` в
  strcmp, strncmp, strcasecmp и в ```__ismask``` из ctype намеренно преобразует
  отрицательный ```char```; именно так и получается беззнаковое сравнение байтов.
```make wp-smoke``` добавляет проверку на вырожденность: цель падает, если контракт
выполняется лишь потому, что код недостижим.

## Воспроизведение доказательств

Протоколы доказательств лежат в ```sessions/```: ```cache/``` (результаты солверов),
```script/``` (тактики WP), ```interactive/``` (доказательства на Coq),
```reports/``` (пофункциональные срезы ```-wp-report-json```).

Каталог ```sessions/``` помечен в ```.gitattributes``` как ```-diff
linguist-generated=true```, поэтому эти файлы не попадают в ```git diff```, в ревью на
GitHub и в статистику языков. Посмотреть их всё же можно через
```git diff --text -- sessions/```.

```make wp-replay``` воспроизводит доказательства из кеша, не запуская солверы. Кеш WP
привязан к точному хешу цели и версии солвера — в отличие от shape-ов Why3 он не переживает
правок исходника; ```make wp-rebuild``` пересобирает его.

В репозиторий попадает кеш только для функций, отмеченных как доказанные в колонке WP, и
только записи, фиксирующие доказательство. ```make wp-prune``` пересобирает его именно на
этой основе. Закешированные timeout-ы не коммитятся: это устаревшие отрицательные
результаты, скрывающие цели, которые новый солвер уже может закрыть.

## Анализ значений

```make eva``` запускает плагин Eva на libFuzzer-обёртках как независимый поиск ошибок. Он
намеренно не объединяется с запуском WP: свойство, помеченное Eva как доказанное, WP
пропустил бы, а Eva здесь видит лишь синтетическую обёртку.

# Организация файлов в репозитории

Каждая библиотечная функция ядра Linux располагается в отдельном *.c файле. В соответствующем *.h файле находятся объявления, типы, структуры, специфичные для данной функции.
- В **kernel_definitions.h** файле находятся общие для всех функции типы, макросы и прочие декларации.
- В **ctype.h** находятся сразу несколько функций, которые изначально в ядре были макросами. Для удобства формальной верификации данные макросы (islower,isupper,isdigit,...) были переписаны как inline функции.

# Как добавить новую функцию в репозиторий

В [репозитории](https://github.com/evdenis/spec-utils/) есть инструмент extricate. Он используется для того, чтобы "выцепить" код функции в отдельный файл.
Пример (код для функции strim):
```
$ extricate -m ~/linux-stable/lib/string.c -k ~/linux-stable --double -f strim --output-dir .
```
Будет сформировано два файла: strim.c и strim.h
* Опция **-m** - путь к файлу с определением функции.
* Опция **-k** - путь к директории ядра.
* Опция **--double** - формировать два файла *.h и *.c
* Опция **--f** - имя функции
* Опция **--output-dir** - директория для вывода файлов

# Организация спецификаций

Контракт (предусловие и постусловие) находятся для каждой доказанной функции в соответствующем заголовочном файле (например, strlen.h). В нем же находятся леммы/аксиомы/логические функции, если они разработаны для соответствующей функции.

В *.c файле находится тело функции с инвариантами циклов, оценочными функциями и ассертами.

Для некоторых функций спецификации избыточны и фактически дважды по разному описывают то, как функций должна функционировать. Например, одна из таких функций - strlen. В её спецификации есть обычные функциональные требования и есть требование на соответствие возвращаемого результата вызову логической функции под тем же названием strlen. Чем мотивирована подобная "избыточность"? Логическую функцию strlen удобно использовать в спецификациях других функций, например, strcmp (а логическую функции, описывающую поведение функции strcmp при описании функциональных требований к strcpy). При этом все основные свойства логической функции выражаются через леммы (каждая лемма — это цель доказательства, см. ниже). Такие спецификации невозможно отобразить в проверки времени исполнения E-ACSL. Поэтому для тех функций, которым в спецификациях ставится в соответствие логическая функция, обязательно есть и "обычные" спецификации.

Как выбирается будет ли для функции разработана такая избыточная спецификация?
1) Обычной функции можно сопоставить логическую функцию (один-в-один), только если функция на языке Си "чистая" (pure).
2) Логическую функцию рационально писать в том случае, если они пригодится для разработки спецификаций в том числе и для других функций. Например, в функциональных требованиях к memcpy можно выразить "одинаковость" src и dest посредством вызова логической функции memcmp.

Для каждой ```lemma``` WP порождает отдельную цель доказательства. При этом WP может
использовать её как гипотезу в других целях ещё до доказательства самой леммы, поэтому
одних зависимых целей недостаточно. Ранее недоказанная ```strcmp_corollary``` теперь
доказана как ghost-функция в **match_string.h**. Под AstraVer индуктивные леммы
доказывались лемма-функциями плагина; теперь они лежат в заголовочных файлах как обычные
ghost-функции ACSL, контракт которых доказывает WP, а вызывающий код инстанцирует их из
ghost-кода — см. блок после каждой аксиоматики в **strlen.h**, **strnlen.h** и других.

Постулируются, а не доказываются, 76 ```axiom``` в **ctype.h**, **strncasecmp.h** и
**hex2bin.h**: они табулируют ```tolower```/```toupper``` и ```hex_to_bin``` по набору
символов. Их никто не проверяет, и противоречие в них сделало бы каждую зависящую от них
цель тривиально доказуемой; заметить это может только ```make wp-smoke```.

Три файла — **strrchr.h**, **strim.c** и **memcmp.c** — по-прежнему содержат старую
аксиоматику внутри обычного комментария ```/* */```, а не ACSL-комментария ```/*@ */```.
Этот текст неактивен: он не разбирается, не доказывается и нигде не используется.

# Интеграция с LibFuzzer

[LibFuzzer](http://llvm.org/docs/LibFuzzer.html) - библиотека для фаззинга функций. Для части  функций произведена соответствующая интерграция с данной библиотекой. Для того, чтобы можно было запустить фаззинг, необходио иметь в системе компилятор clang, а в корне директоии библиотеку libFuzzer.a
Запуск фаззинга:
```
$ make fuzz-<func>
$ make fuzz-check_bytes8
```
